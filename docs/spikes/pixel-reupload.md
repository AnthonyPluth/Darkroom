# Test re-uploading generated videos from a first-generation Pixel

Use this runbook for V1–V5 in the [Google Photos video re-upload design](../design/google-photos-video-reupload.md#disposable-tests-to-record-on-266). Run only with a separate Google account, an isolated first-generation Pixel, and generated files. Use a disposable Immich owner and recovery point. Before an item leaves the live library, verify the exact generated bytes in Immich and on the Pixel, check current recovery-point coverage for the Immich asset, and confirm fresh Syncthing completion after its scan indexed the staged file. Record local file and cloud item identifiers privately to keep the test actions tied to the right item. [Recovery-point gate](../design/recovery-point-gate.md)

## Generate and compare files

Install FFmpeg with `libx264` on the machine where you prepare files. From a Darkroom checkout, run the command with an unused directory path outside any existing photo library. It creates that directory and prints the generated names, sizes and SHA-1 digests. Use the printed measurements when planning disk space and reporting storage changes.

```sh
poetry run python -m tools.spikes.pixel_reupload prepare --out /tmp/pixel-reupload-test --target-mb 128
```

The target size applies approximately to each of `live`, `trash` and `quota`. `restore`, `purge` and `control` are about 2 MB each. Set the target size below the disposable Pixel's capacity and configured staging cap. If Google One rounds away the change, repeat with larger files or record the quota result as inconclusive. Use a new directory for each attempted generation. A run that stops before printing its inventory may leave partial files.

Upload the same unchanged generated file through the ordinary charged path and, when called for below, from the Pixel. To verify an unedited original downloaded from Google Photos or Immich, or a file copied back from the Pixel, compare it to its generated source. Use the fixture for the row you are testing and substitute your local download path. The response contains the byte counts and match result. The command exits 1 for different files and 2 when it cannot compare.

```sh
poetry run python -m tools.spikes.pixel_reupload compare \
  /tmp/pixel-reupload-test/darkroom-spike-*-live.mp4 /tmp/downloaded-video.mp4
```

## Run V1–V5

On the Pixel, confirm which local folder Google Photos sees, that the staging folder is excluded from automatic backup, and whether **Back up all device folders** is off. Record the Android and Photos app versions and the chosen backup settings. Use the isolated account on the Pixel and in a separate browser. Keep album and share tests limited to fixtures and the disposable account.

| Row | Procedure and evidence |
| --- | --- |
| V1 · Charged baseline | Use `live`. Record the Google One Photos subtotal before and after upload through an ordinary charged path. Identify the specific cloud item and check the charge if Google exposes it. Download its original and compare it with `live`. |
| V2 · Old item live | With the charged `live` item still visible in the web library, stage and sync its exact bytes. Try the per-item Pixel backup at Original quality. Check whether it creates a distinct item, reuses the old one, or does nothing. Check the replacement's quality, exact original bytes and charge separately. |
| V3 · Old item in Trash | Start with a charged `trash` item and its verified staged copy. Turn off backup on devices whose copies must survive. Move only the old item to Trash in the browser. Compare the surviving local copy, try manual Pixel backup, and try only the minimum setting change needed. Record whether the file survived, whether the old item remained restorable and whether a distinct matching Original quality replacement appeared. Separately, use `restore` to observe what Restore returns to the library, test album, and device. |
| V4 · Targeted permanent removal | Use the disposable account only. With `purge` and `control` separately identified in Trash, check whether the browser offers permanent removal of just `purge`. Stop if it offers only an action on the whole Trash. Before permanently removing either target, recheck the Immich original's bytes, current recovery-point coverage, and the exact file's Pixel presence and fresh per-file sync. Verify `control` is still restorable afterward and leave it to observe natural expiry. If deduplication blocked V3, repeat the check with `trash` before trying its same-byte Pixel upload. A purge-first result requires a new design decision for production. |
| V5 · End-to-end evidence | Use `quota` and the order that succeeded with the old item still restorable. Check the new item's separate-browser identity, unedited bytes and Original quality against per-item Pixel backup status and a later Takeout. Record the Photos subtotal before the first upload, with the charged item live, while it is in Trash, after removal has settled, and after the Pixel upload has settled. Isolate other activity in that account. If nothing worked with the old item restorable, record that V5 is blocked. |

A missing local copy, unknown origin, ambiguous duplicate, or mismatch cannot pass its row. The control must remain separately identifiable in Trash with Restore available after the targeted removal. Record quota as inconclusive if the readings cannot show whether the replacement is uncharged.

### Offline Syncthing check for V2 and V3

Two isolated v2.1.7 Linux peers on loopback exercised the indexed-file check. The empty folder reported 100% completion while the read-only `GET /rest/db/file` returned 404 for the target path. Once the target was indexed, that request returned no availability for the offline peer. After sync, the response showed matching local and global `version` and `blocksHash` and listed the receiver in `availability` with `fromTemporary: false`. Completion was 100% with zero needed items or deletes, and a read-back of the receiver copy matched the source SHA-1. A same-size rewrite while the receiver was offline invalidated the old version and block hash. Syncing again produced fresh matching evidence. Use the same read-only checks and a Pixel read-back in V2 and V3 to confirm the Android client reports this evidence. [Pinned Syncthing release](syncthing-api.md#versions) · [File endpoint](https://github.com/syncthing/syncthing/blob/v2.1.7/lib/api/api.go#L918) · [Availability check](https://github.com/syncthing/syncthing/blob/v2.1.7/lib/model/model.go#L2880)
