# Security

Darkroom handles a household's private photos and the keys to the services around them. Read this before touching sign-in, tokens, encryption, the browser worker or anything that deletes a file on Unraid.

## What must hold

- Originals are never modified, moved or deleted by the service (AGENTS.md, "Darkroom's promises", 1 and 2).
- Darkroom decides nothing about deleting a photo from an iPhone: promise 3 is retired (#199) and Immich's own app clears backed-up photos. The deletion path, the device sign-in, the push to iPhones and the tables behind them were removed (#201).
- The browser worker never types a Google password or 2FA code (promise 4). Signing in is done by a person, in the embedded browser view.
- Secrets (API keys, tokens, the secret key, whether from `DARKROOM_SECRET_KEY` or the `secret-key` file generated in `DARKROOM_DATA_DIR`) are never committed, logged, returned in a reply or put in an error message. The generated file is created with mode 0600 and never replaced; `check-config` says which of the two the key comes from, never the key. `.env.example` lists the configuration; real values stay in `.env`.
- Darkroom holds no device (iPhone) or push tokens any more: device sign-in, the `device` auth kind, push registration and revocation were removed (#201), and migration 0025 dropped the `devices` table with every token stored in it.
- Every route declares who may call it (`session`, `worker`, `setup`, `setup-claim` or `public`), and an unlisted kind answers 401. A new route needs a test.
- The first-run setup routes (`setup` and `setup-claim`, under `/api/setup`) are the one way in without signing in, and only with `DARKROOM_WIZARD=1`. Before anyone has signed in and while no sign-in is set up, the first browser that claims the wizard holds it (a random cookie, stored hashed). It must connect directly from a private address (10/8, 172.16/12, 192.168/16, loopback, fc00::/7) with no forwarding header and with a `Host` and `Origin` checked as for running without sign-in. Every other caller, signed-in members included, gets 401. The window closes for good at the first successful sign-in or test sign-in; `run.py reopen-setup` clears a lost claim but reopens nothing once anyone has signed in. Stored `OIDC_CLIENT_SECRET` and `RESEND_API_KEY` are sealed with the secret key and never shown, only whether they are set. The address check trusts the TCP peer, so the wizard must not be on while the port is reachable from outside the LAN through Docker's userland proxy (IPv6 included) or a port forwarder (`docs/runbook.md`, "The first-run setup API").
- Without sign-in (`DARKROOM_ALLOW_NO_AUTH=1`), a session route answers only a request whose `Host`, and for a state change its `Origin`, is an IP address, `localhost`, the host of `DARKROOM_HOST` or `DARKROOM_PUBLIC_URL`, or a name in `DARKROOM_ALLOWED_HOSTS`, so a DNS-rebound page gets nothing (`docs/runbook.md`, "Running without sign-in").
- Darkroom holds no APNs key: the APNs provider and its `APNS_*` settings were removed (#201). Alerts go out only as email to the one owner address through Resend, when it is set up (`docs/deploy/alerts-email.md`).
- Outbound requests go through `darkroom/tls.py`; subprocesses only through `darkroom/providers/exiftool.py` (and the worker's runner, and in the one container `darkroom_init/supervisor.py`, which starts the processes and checks the display is up).

## Accepted scanner findings

The image scan fails on any CRITICAL or HIGH vulnerability with a fix. A finding that can't be fixed yet and doesn't apply is accepted only in `.trivyignore.yaml` at the repository's root. The list takes effect only once `.github/workflows/security.yml`'s `single-image` call passes it as fleet's `trivy-image-ignore-file` (fleet 4.1.0 and later; until the fleet bump that adds that input is merged, nothing reads the list and the scan still fails). Each entry is limited to one exact path in the image (no wildcards, so the same CVE anywhere else is still reported), quotes the owner's acceptance, carries a one-line reason and an `expired_at` at most 180 days away, after which the finding is reported again and renewing it is a new pull request. `tests/test_trivyignore.py` holds those limits. The image scan reads the list only from the tip of `main`, never from a pull request's checkout, so an entry counts once it has been merged, and the pull request that adds one doesn't benefit from it. Merging is the owner's act by decision, not something the ruleset enforces: Code Owner review is off, so the list's `.github/CODEOWNERS` entry asks for the owner's review without requiring it, and every change to the list gets the Second review. From fleet 4.1.0 neither Trivy scan reads Trivy's own `.trivyignore`, `trivy.yaml` or `trivy-secret.yaml` from the checkout, so this list is the only thing that accepts a finding.

Accepted now:

- CVE-2026-78661 (HIGH, `golang.org/x/net` v0.60.0) in `usr/local/bin/syncthing`, the pinned Syncthing v2.1.7 (#341), until a fixed Syncthing is pinned or 2027-02-14, whichever comes first. The owner accepted it on #341 (https://github.com/AnthonyPluth/Darkroom/issues/341#issuecomment-6926210618): "Add ignore-file support to fleet (Recommended)" and "Since darkroom isn't deployed, let's just merge with these CVEs and fix when fleet bump is merged in so we can keep moving". Why it doesn't apply: the vulnerable `x/net/html` package is not linked into the binary (the binary's Go build info and symbol names list 12 linked `x/net` packages, none of them `html`), Syncthing's API is only on a private `0600` Unix socket, and no Syncthing release with a fixed `x/net` exists yet.

## Reporting a problem

Open a private security advisory on this repository, or tell the owner directly. Please don't open a public issue with details.
