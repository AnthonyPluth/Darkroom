# Verify Darkroom in the real app

`tools/control` drives the real app on made-up demo data: a demo server under make verify's frozen clock and a Chromium signed in as the demo member, kept alive between commands. Every command prints JSON (`--text` for a readable form); a failure is `{"ok": false, "error": {code, message, hint}}`, and the hint says what to do next.

Use it while you work, to see what you changed. `make verify` is the batch check (every page at phone 440×956 and desktop 1280×800, the flows, the accessibility audit) and the only source of the images in `docs/screenshots/`.

## The loop

1. **Launch.** `tools/control doctor --text`, then `tools/control start`. It refuses a busy machine (`--anyway` overrides) and leaves a running make verify alone. Rebuild first (`cd frontend && npm run build`) after a change under `frontend/src`, or you see the old app; a session started before the build keeps serving the old files until `reset`.
2. **Drive.** `goto <page>` (`status`, `people`, `sign-in`, or a path such as `/exports`), `snapshot --text` (the roles and names to target), `click button "Add person"`, `type textbox Name 'Sam Example'`, `press Escape`, `viewport desktop`, `flow <name>`.
3. **Prove.** `screenshot` at `viewport phone` and at `viewport desktop`, then open each image and look at it. Read `console` and `network`: make verify fails a page on a console error or a 5xx, so treat them as failures too.
4. **Clean up.** `tools/control stop`. After a crash: `tools/control cleanup`.

## Screenshots for a pull request

A pull request that changes the web app carries screenshots (AGENTS.md, promise 6), and they come from one place: run `make verify` and commit what it writes to `docs/screenshots/` (`<page>-phone.png` and `<page>-desktop.png`; they are the visual baselines, and the owner compares them with `docs/design/web/`). Never put an image from `artifacts/control/` or a hand-made file in a pull request: `tools/fleet checks` fails an image anywhere but where `make verify` writes it. Add the page to `PAGES` in `frontend/verify/verify.mjs` (and its path to `ROUTES` in `routes.mjs`) when your issue adds a page.

## Evidence to attach

- The commands you ran and what they returned (paste the JSON or `--text`).
- What you saw in the screenshots at phone and desktop.
- The images `make verify` wrote, for the pages your change touches.

## Safety

- Demo data only, on the session's own loopback server, with none of your real settings (no `DATABASE_URL`, sign-in provider, Immich key or secret key reaches it) and no way out to the internet: the browser blocks every request to an address other than the session's server before it is sent, and the server gets only a short list of environment variables. No real Google, iPhone or Immich is ever involved. It refuses other URLs.
- The repository is public: put no real data (names, photo file names, locations, emails, Google data) in commands, flows, screenshots or PR text.
- What it reports is scrubbed: requests as paths with ids as `:id` and never a query string, console text without amounts, email addresses or long tokens.
- Everything it writes is under `artifacts/control/`, ignored by git. Never commit it.
- `eval` is read-only unless you pass `--write`; changes the page tries to make while a command that only looks (snapshot, screenshot, eval) is running, or between commands, are blocked and reported. `reset`, `stop` and `cleanup` take `--dry-run`.
